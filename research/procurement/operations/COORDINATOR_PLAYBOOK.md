---

## 1. Overview & Operational Principles

As Coordinator, your role is to maintain epistemic integrity, prevent cross-process duplication, and safeguard the codebase from unauthorized scope creep—with minimum administrative overhead and zero unnecessary meetings.

### Core Governance Principles:
1. **Asynchronous Quality Control:** Reviews happen directly on GitHub PRs. Do not schedule synchronous review meetings when inline comments suffice.
2. **Strict Scope Discipline:** If a PR touches code outside `research/procurement/`, halt and reject it immediately.
3. **Evidence Over Enthusiasm:** Reject generic marketing hype. Require verbatim quotes, canonical URLs, and honest epistemic tagging.

## 2. Step-by-Step PR Evaluation Procedure

When a team member opens a Pull Request:

```text
[PR Notification]
       │
       ▼
[1. Automated CI Audit] ──► (Fails?) ──► [Auto-Halt: Request CI Fixes]
       │ (Passes)
       ▼
[2. Scope Boundary Check] ──► (Touches src/ or other processes?) ──► [Reject / Request Scope Trim]
       │ (Clean)
       ▼
[3. Evidence Quality Audit] ──► (Fabrication or missing URLs?) ──► [Request Changes]
       │ (Solid)
       ▼
[4. Ambiguity & Contradiction Check]
       │
       ▼
[5. Approve & Fast-Forward Squash/Merge into main]
```

### Step 1: Inspect Automated CI Summary
Open the GitHub Actions run under the PR. Check the **Job Summary** generated by `.github/workflows/procurement-pr-check.yml`:
- Confirms zero broken relative links.
- Confirms all edited files belong strictly to the author's assigned process directory.
- Confirms required evidence table columns and valid ID patterns.
- *If CI fails:* Do not spend time reviewing content. Comment: *"Automated checks failed; please resolve local validator errors."*

### Step 2: Verify Scope & Ownership Boundaries
Review the PR's **Files changed** tab:
- Ensure **only** the contributor's assigned process folder is modified:
  - Vrushali $\rightarrow$ `research/procurement/processes/P02-SUPPLIER-DELIVERY/`
  - Bhushan $\rightarrow$ `research/procurement/processes/P03-REPLENISHMENT/`
  - Ashwin $\rightarrow$ `research/procurement/processes/P04-INVOICE-EXCEPTIONS/`
  - Chiranjeevi $\rightarrow$ `research/procurement/processes/P01-RFP/`
- Ensure zero files in `src/`, `contracts/`, `data/`, or `package.json` are present in the diff.

### Step 3: Audit Evidence Claims Against Quality Gate
Sample 2-3 newly added evidence entries against [`EVIDENCE_QUALITY_GATE.md`](./EVIDENCE_QUALITY_GATE.md):
- Spot-check the source URL in a browser.
- Verify the quotation appears verbatim in the cited document.
- Confirm evidence level:
  - Is a public blog or vendor marketing piece incorrectly marked as `E4` or `E2`? Demote to `E0` or `E3`.
  - Is synthetic data from `RFP-001` cited as empirical evidence? Reject immediately.

### Step 4: Handle Contradictions & Unknowns
- If findings contradict an existing process claim, verify that both viewpoints are captured in [`../AMBIGUITIES.md`](../AMBIGUITIES.md) rather than one being silently overwritten.
- Ensure any `A3` or `A4` ambiguities are addressed or consciously accepted as open questions.

### Step 5: Issue Verdict & Merge
- **To Request Changes:** Click "Review changes" $\rightarrow$ "Request changes" $\rightarrow$ leave bulleted actionable comments.
- **To Approve & Merge:**
  ```bash
  gh pr review <pr-number> --approve --body "Approved: Verified evidence grounding and scope discipline."
  gh pr merge <pr-number> --squash --delete-branch
  ```
  *(Using squash-merge maintains a clean, linear git history on `main`).*

## 3. Resolving Ownership & Drift Conflicts

- **Symptom:** Researcher A writes a section on invoicing inside their delivery folder.
- **Resolution:** Remind the researcher of the boundary rule: *"Delivery delays belong in P02; their financial matching consequences belong in P04. Please add a cross-process reference (`WF-P02-005 -> P04`) instead of duplicate analysis."*

---

## 4. Recovering from an Erroneous Merge

If a PR was merged by mistake that introduced invalid data or broken links:
```bash
# 1. Update your local main
git checkout main
git pull origin main

# 2. Revert the squash commit
git revert -m 1 <commit-hash>   # or git revert <commit-hash> if squashed
git push origin main
```
Never force-push to `main` to rewrite history. Always use `git revert`.
